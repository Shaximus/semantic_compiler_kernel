My assessment: the architecture is coherent, the threat model is useful, and there are several important issues to resolve before awarding GOLD.

### 1\. What you've established

The strongest decision is in Section 1:

> A defensive component may detect, evaluate, recommend, deny, and halt within its explicitly granted scope. It may never cross from verifying a boundary to redefining the boundary, the principal, or its own authority.

That is the central invariant.

The specification also correctly recognizes that zero self-escalation is insufficient. A compromised supervisor could preserve its nominal permissions while starving the override channel, manipulating telemetry, or holding the system in perpetual quarantine.

That's why AC-2 through AC-5 matter.

### 2\. Five technical issues I'd resolve before implementation

| Invariant | Assessment                                   | Required refinement                                                     |
| --------- | -------------------------------------------- | ----------------------------------------------------------------------- |
| AC-1      | Sound objective                              | Define indirect delegation and capability inheritance                   |
| AC-2      | Important, but mathematically underspecified | Define causal non-interference over authorized principal actions        |
| AC-3      | Strong recovery requirement                  | Define adversary and hardware failure assumptions                       |
| AC-4      | Correct separation                           | Define exactly which permissions historical compliance cannot influence |
| AC-5      | Essential                                    | Define bounded quarantine renewal and recovery semantics                |

Three issues deserve particular attention.

A. AC-2 needs refinement.

The current expression:

P(\\mathcal A'_{\\text{protected}}\\mid do(m))
=
P(\\mathcal A'_{\\text{protected}})

could be interpreted as requiring the authority plane never to change when a monitor is involved.

But legitimate principal actions may change it.

The intended property is:

\\Delta\\mathcal A_{\\text{unauthorized by }m}=0

In other words, monitor intervention must not cause unauthorized changes, while legitimate principal-authorized changes remain possible.

I'd define the permitted transition relation explicitly.

B. AC-3 needs a fault model.

An override channel cannot be guaranteed against every conceivable failure.

Specify whether the guarantee assumes:

* The principal's hardware root remains operational.

* The override transport remains available.

* The operating system or independent control plane remains trustworthy.

* The attacker cannot physically compromise the override mechanism.

Then define under those assumptions.

C. The reference implementation has a possible authorization ambiguity.

Section 5 contains:

```python
if check.actor_role != AuthorityRole.PRINCIPAL:
    if check.target_is_authority_plane or check.target_is_principal_override:
        return False
return check.action in ALLOWED_ROLE_ACTIONS.get(check.actor_role, frozenset())
```

This is a useful initial allowlist, but the check does not independently establish that the actor is an authenticated principal authorized to perform the requested action.

The role label itself must not be trusted as proof of identity.

Also, the implementation needs to consider protected resources, delegation, and indirect tool calls, not just direct role-action pairs.

### 3\. One particularly important missing test

I'd add:

TEST-AC-06: Principal Identity Integrity

Attempt to impersonate the principal through:

* A forged `actor_role`.

* A substituted principal identifier.

* A compromised agent forwarding a principal-looking request.

* A stale or revoked principal credential.

* A compromised policy engine returning a fabricated authorization verdict.

Expected result: no authority-plane mutation without independently verified principal authorization.

This closes a gap between the graph's conceptual role separation and actual identity authentication.
